# Liveness Verification Architecture Decision Guide

Architecture Decision Record (ADR)

## Problem Summary

The current architecture allows the **client (browser)** to decide
whether liveness passed. The frontend builds a payload containing values
such as:

```json
{
  "final_liveness_result": "passed",
  "challenge_results": [
    { "passed": true }
  ]
}
```

If the backend trusts these values, an attacker can bypass the UI
completely and directly call the API with a forged request. In other
words, the security decision is made on the attacker's machine instead
of the trusted server.

**Core Principle**

- **Client:** Collect evidence.
- **Server:** Make the security decision.

---

# Option 1 --- Client Decides the Verdict

## Working

- Browser runs MediaPipe.
- Browser evaluates challenges.
- Browser sends `passed/failed`.
- Server trusts the client's verdict.

## Evaluation

  Metric        Rating

---

  Reliability   ★☆☆☆☆
  Cost          ★★★★★ (Very Low)
  Accuracy      ★★★★☆ (for honest users)
  Durability    ★☆☆☆☆

### Pros

- Fastest implementation.
- Lowest infrastructure cost.
- Minimal backend processing.
- Excellent UI responsiveness.

### Cons

- Not secure.
- Easy to bypass.
- API can be scripted.
- Unsuitable for production identity verification.
- Fails compliance/security audits.

---

# Option 2 --- Server Decides Using Client Measurements

## Working

- Browser runs MediaPipe.
- Browser sends measurements (yaw, timestamps, challenge sequence).
- Server evaluates pass/fail using those measurements.

## Evaluation

  Metric        Rating

---

  Reliability   ★★★☆☆
  Cost          ★★★★☆ (Low)
  Accuracy      ★★★★☆
  Durability    ★★★☆☆

### Pros

- Server owns the verdict.
- Better separation of responsibilities.
- Easier to evolve server-side rules.
- More difficult to bypass than Option 1.

### Cons

- Client measurements can still be fabricated.
- Does not fully solve trust issues.
- Not recommended for high-security identity systems.

---

# Option 3 --- Server Owns Both Evidence and Verdict (Recommended)

## Working

1. Browser captures images or a short video.
2. Browser uploads evidence to the server.
3. Server extracts landmarks.
4. Server computes yaw and challenge completion.
5. Server performs liveness verification.
6. Server generates the final verdict.
7. (Optional) Server generates face embeddings and compares them with
   the stored encrypted embedding.

## Evaluation

  Metric        Rating

---

  Reliability   ★★★★★
  Cost          ★★☆☆☆ (Highest)
  Accuracy      ★★★★★
  Durability    ★★★★★

### Pros

- Strongest security.
- Server is the single source of truth.
- Difficult to bypass.
- Suitable for production.
- Supports secure face recognition.
- Easier to meet regulatory/compliance requirements.
- Scales well as new liveness checks are added.

### Cons

- Highest compute requirements.
- Increased bandwidth (image/video upload).
- More backend complexity.
- Requires GPU/CPU resources depending on scale.

# Recommendation

For a system whose end goal is:

- Face registration
- Secure liveness detection
- Face recognition using stored encrypted embeddings
- Identity verification

**Option 3 is the correct long-term architecture.**

Although it has the highest infrastructure cost, it is the only option
where: - The server is the trusted authority. - Liveness cannot be
forged by modifying the browser. - Face recognition and liveness are
performed within the same trusted environment. - The design remains
secure and maintainable as the system evolves.
